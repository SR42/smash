# Test suite: what each test guards

Why each test exists, what it asserts, and how it was verified as a real discriminator. Moved from CLAUDE.md; read the entry for a test before changing it or its threshold.

## End-to-end tests under interposition

All 81 tests must pass; none are registered `DISABLED`. Run the suite **as root** too when touching the compressor: some paths only exist with root (see "Idle-page read tracking" in [defect-history.md](defect-history.md)), and an unprivileged run — which is all CI does — never executes them. CI (`.github/workflows/ci.yml`) runs the full suite on `ubuntu-latest` and `macos-latest` on every push and PR. Twenty-eight of the tests are end-to-end under `DYLD_INSERT_LIBRARIES` / `LD_PRELOAD`:

- `test_arena_routing` guards call-site arena routing — the invariant behind the paper's compression-homogeneity claim. Runs a program with 32 distinct noinline allocation sites under interposition and asserts, via the exported `smash_arena_for(ptr)` query, that they do **not** all collapse into one arena. This is the regression guard for the LTO/wrapper return-address bug: under dynamic interposition the return address seen inside the allocator can point into the wrapper library instead of the app, collapsing every call site into one arena (homogeneity 0%). Fast and deterministic (no compressor): full mode routes 256 B allocations through the slab, and `SMASH_CPU_ARENA=0` + default thread-hash-off make the arena a pure function of the return address, so a buggy capture yields exactly 1 distinct arena. Verified as a real discriminator (injecting a constant RA makes it fail with `distinct_arenas=1`). Must run under interposition — a direct-linked call would never exercise the wrapper path where the bug lives.

- `test_malloc_numa_{full,large_only}` and `test_numa_arena` guard `malloc_numa(node, size)` (`include/smash/smash.h`). It serves page-granular blocks from per-node arenas inside the VmRegion (see Key Conventions in CLAUDE.md).
  - **`malloc_numa_test.cpp`** runs under preload in both modes. For every online node it asserts that `get_mempolicy(MPOL_F_ADDR)` reports exactly `MPOL_BIND | MPOL_F_STATIC_NODES` on `{node}`, and that `move_pages` reports every written page on that node. The writer is pinned to off-node CPUs first, so first-touch locality can't put the pages there by accident. It then leaves a 16 MiB block per node cold (`SMASH_COLD_TIMEOUT_SEC=1`) and waits for its pages to leave RSS (`mincore`). It reads the blocks back from off-node CPUs and checks they are byte-exact, with every page on the node and the policy intact. It also checks heap-block semantics, `EINVAL` for bad nodes, that freed blocks are reused (below), and that ordinary `malloc` memory carries no policy.
  - **Reuse check, rewritten 2026-09-29.** It used to require 16 of 16 free/re-allocate rounds to return the **same address**. That failed twice as root on the 2-CPU claudepc (2026-09-24 UBSan `full`, "12 of 16"; 2026-09-29 `large_only`, "15 of 16"; about 4 in 100 root runs there when looped). **Cause, confirmed harmless:** `free()` queues a node block for the node's decommit thread, and on a loaded 2-CPU host the queue sometimes lagged the loop's 20 ms sleep by a few rounds, so best fit correctly took the next free run of the same node arena. Instrumented misses all had carved +0 pages, a smash-owned block bound to the node, and free pages short by one block per lagging round, all back once the queue drained. The address was an over-strict proxy for the contract, which is **no growth and no leak**. The check now asserts, per node, via `smash_numa_arena_info`: every block is smash-owned and bound to the node; carved pages unchanged across the 16 rounds; free pages after the queue drains (two equal readings 50 ms apart, up to 5 s) equal to before. **Verified by mutation** in `processDecommitEntry`: sending node frees to the shared free map, or dropping them, fails with "15607 free pages before the rounds, 11511 after the queue drained" (16 blocks × 256 pages missing). Rewritten check: 0 failures in 50 root runs per mode on claudepc.
  - **`test_numa_arena.cpp`** is direct-linked and deterministic. It covers grid-aligned chunks, the gap skipped below a chunk and a bad node's chunk becoming unbound shared pages, free-list reuse within a node, and `remapPages()` binding a replaced node page again, including a remap that straddles a shared page and a node page.
  - **Verified as a real discriminator** on a 4-node host:
    - not installing the remap hook fails the arena test's three remap checks;
    - routing freed node pages to the shared free lists fails the arena test's shared-list and reuse checks on all 4 nodes. End to end, 0 of 16 frees come back at the same address, and the binding leaks into a later `malloc(256)`;
    - never marking node blocks `ACTIVE` fails the compression check: 0 of 4096 pages leave RSS in 30 s on every node.
  - Skips on `ENOSYS`/`EPERM` from `mbind`. Single-node CI runners cover node 0 only, with no off-node pin.

- `test_shared_arena_churn_{full,large_only}` and `test_arena_reclaim_concurrent` guard the **shared** arena — the one every ordinary large allocation uses (`shared_arena_churn_test.cpp`, `SMASH_VM_GIB=1`). `VmRegion::allocatePages()` had the same defect the NUMA node arenas did, and worse: it called the exhausted hook, retried `take()` **once** and returned nullptr, with **no drain at all**, so a freed run still queued for decommit was indistinguishable from one that was gone and the caller got a direct mapping that is never compressed. Measured with 2 MiB blocks through a 1 GiB arena: 0 of 40000 single-threaded (the decommit thread keeps up), then **1728 of 40000 at 4 threads, 46263 of 160000 at 8, 93726 at 16 and 144241 at 64** — up to 90% of allocations silently uncompressible. After the same `drainDecommitQueueNow()` + `drainInFlight()` retry the node path uses: 70 / 84 / 129 / 174, flat in thread count. **Verified as a real discriminator:** removing the retry fails phase A with ~146000 blocks against an allowance of 800.

  **The residual was not harmless (2026-09-26).** Phase A failed on the 128-core aarch64 box with 1192 and 1173 blocks out (allowance 800), and three copies at once gave 466-548 here. Traced on the 25th: at every fallback the whole arena (~512 runs) was pending in the decommit queue, the free map empty, another thread mid-drain, and the waiter had used up its 64 `sched_yield`s (0.1-1 ms, up to 42 ms under load); the drain was slow because every entry did `mprotect(RW)` — the process's `mmap_lock` for writing — even when no page was compressed: 0.8 us alone, 251 us at 32 threads, and the `madvise` after it 6.7 -> 123 us. Fixed both: the wait is time-bounded (at least 64 tries, then up to 50 ms while runs are in flight) and a run whose release reported no COMPRESSED page skips the `mprotect`. Measured against the previous library: **0 blocks out** idle, loaded and in both modes (was 188-264 idle, 466-548 with three copies); the timed wait alone also gives 0, the skip alone 23-85; the phase runs in 1.1-1.3 s instead of 2.3-2.5. The allowance is now 0.05% (80), below what the counted wait left here (130-274), so the previous library fails it on this host (3 of 3) and the fixed one passes.

  **Phase B is a guard, not a reproduction, and the difference matters.** `Slab::reclaimEmptySpans()` skips a slab whose lock it cannot `tryLock` — the caller may already hold another slab's lock, so blocking could deadlock — and a skipped slab is a negative answer that is not authoritative, the same shape as the bug above. It **does not reproduce**: filling the arena with small objects, freeing them, and then taking 200 × 2 MiB while 8 to 32 threads churn small objects across eight size classes gives 0 of 200 outside the arena, every run, with a control (the same request while the small objects are still live) showing 200 of 200 falling back to prove the arena really was exhausted. The phase is kept because the invariant is worth pinning, and it does catch a disabled exhausted hook (182 of 200).

  **Under CPU contention it does reproduce** (measured 2026-09-23). With eight busy loops on the 8-CPU host, phase B fails with 145–168 of 200 blocks outside the arena — the same magnitude as a disabled hook: 1–2 runs in 30 on the normal build and 2–5 in 15 under UBSan, whose slowdown widens the window. It is **not a regression** from the changes that were being tested when it surfaced: interleaved, the pre-change library, the changed one and the changed one minus its only free-path edit fail at the same rate (1, 1 and 2 of 30). Unloaded it passes (0 of 60 direct runs, 0 of 32 through ctest), which is why a quiet suite stays green — and why one failure in a full UBSan run, while another job was using the machine, is this and not a new bug. On a 2-CPU host (claudepc) it was not intermittent at all: 9 of 10 runs failed with the changed library and 10 of 10 with the pre-change one, and phase B failed in both root suites there.

  **Fixed (2026-09-23), and the cause was not a brief lock hold.** Instrumenting the exhausted hook on claudepc showed a noisy thread running out first and starting a reclaim pass, which took the slab holding ~63000 empty 256-byte spans and released them one at a time — an mprotect, an madvise and a free-map insert each, ~120 ms. For that whole time every one of the main thread's 2 MiB allocations ran its own pass, found that slab locked (`skipped_slabs=2..5, holding ~63091 -> 45335 empty spans`), got nothing, and fell back — while the pages trickled into the free map in runs of 256-512 pages. A passing run is the one where the main thread happened to run the pass itself. Same shape as phase A: a negative answer that was not authoritative.

  Two changes. `reclaimEmptySpansHook` serialises passes: a thread that runs out while a pass is in progress waits for it, and runs its own only if no pass that started after it arrived has finished (the atfork child handler releases the token). And `Slab::reclaimEmptySpans` releases adjacent spans as one run — the empty list is nearly address-ordered (42000 spans formed 7 runs), so no sort is needed — which took a pass from 82-123 ms to 2-38 ms, and that is now the longest any allocation waits. `SMASH_NO_RECLAIM_WAIT=1` restores concurrent, skip-as-empty passes.

  **Verified on claudepc, interleaved, 10 runs each:** fixed 0 failures; batching alone (`SMASH_NO_RECLAIM_WAIT=1`) 3 (37-181 blocks out); pre-change 9 (88-154). The wait is the fix; batching only shrinks the window. Throughput with a genuinely full arena (8 threads missing at once) is unchanged within noise (2.1-2.4 ms vs 1.9-2.5 ms for 16000 malloc/free), and a 2 MiB allocation's latency in phase B's shape stays under 22 us p100 locally on both builds.

  The phase still needs a contended host to fail on the broken code — it passed 12 of 12 unloaded here even with the old code — so the 8-CPU suite does not prove the fix; claudepc (2 CPUs) or eight busy loops alongside does.

  **Two harness traps, both of which produced convincing false failures.** The phases cannot share a process: phase A's churn leaves the free map without the long runs phase B needs (171 of 200 outside the arena, against 0 in isolation), and phase B's leftovers fragment the arena for phase A (a steady 70–174 residual became an occasional 1293). Splitting them with `fork()` is worse — smash's background threads can hold a slab lock at the instant of the fork, and the child inherits it locked by a thread that does not exist there, so `reclaimEmptySpans()`'s `tryLock` can never succeed for that slab. Phase B then failed 3 runs in 6 with ~170 of 200 blocks outside the arena: **the harness reproduced the exact symptom of the bug it was written to hunt.** They are separate ctest registrations now, one phase per process.

- `test_numa_arena_churn_{full,large_only}` guard that a `malloc_numa` churn loop keeps **reusing** its node arena instead of taking fresh region (`numa_arena_churn_test.cpp`, `SMASH_VM_GIB=1`). A node arena serves from its own free runs, then its newest 64 MiB chunk's tail, then a freshly carved chunk — and `free()` does not put a run back in the free map directly, it queues it, so a tight loop keeps missing the map by microseconds. The miss used to go straight to fresh region, which consumed the arena and then served allocations from separate bound mappings that smash **never compresses** — silently, since the block still works.

  Measured before the fix with a 1 GiB arena: 64 KiB blocks touched all 1023.9 MiB of it and 4.5% of single-threaded allocations fell out; at 16 threads over 4 nodes, **87%** did (285,955 of 320,000). The same loop with 50 us of slack per iteration reused a **0.8 MiB** window and never fell out — which is what identified the decommit queue rather than fragmentation, and is the control worth repeating: if slack fixes it, the free map is not short of pages, it is late with them.

  An allocation that misses now calls `drainDecommitQueueNow()` and looks again before taking anything new, and drains once more before returning ENOMEM. After: 0 of 100,000 fall out single-threaded (arena span 1023.9 → 63.9 MiB, one chunk) and 0 of 320,000 at 16 threads. **Verified as a real discriminator:** the same test binary against the pre-fix library fails 5 checks, with nodes 1–3 reporting 100,000 of 100,000 blocks outside the arena.

  **What the concurrent phase can and cannot guard — worth reading before touching its threshold.** It catches a catastrophic regression: with no drain at all, 285955 of 320000 blocks (87%) fell out. It does **not** reliably catch the subtler race it was first written for. That residual scales with real parallelism and varies run to run — 0–8 of 320000 at 64 threads on an 8-CPU host, 34–529 at 256 threads there, **1537 at 256 threads on a 128-CPU host** — and the unfixed code overlaps it from below (203 at 64 threads on the small host), so no fixed threshold separates them on every machine. A ratio does not either: the same A/B measured 3x on one run and 37x on the next. Three rounds of threshold-chasing across two machines established that; the ceiling is now 2%, an explicit catastrophic-regression guard, and the **single-threaded phase carries the precise assertion** — it is deterministic, it caught the original defect at 4.5%, and it is 0 on both hosts.

  `SMASH_NO_DRAIN_WAIT=1` restores the pre-fix give-up-immediately behaviour, so the wait's value can be measured deliberately on the machine in question instead of inferred from a threshold. Both churn tests also take `SMASH_TEST_THREADS`, which is how a 128-CPU host's behaviour was reproduced without one.

  **A concurrent allocation must also wait for frees that are still in flight.** The first version of this fix took the whole queue with one `decommit_head_.exchange(nullptr)`, so exactly one thread got it and every other concurrent caller saw an empty queue, concluded nothing was recoverable, and fell back to an uncompressible mapping — while another thread was holding those very pages mid-drain. Reported from an aarch64 host as 20 of 320000 blocks (and 11 in large-only) falling out of the arena with the single-threaded phase completely clean, which is the signature of a race rather than capacity or page size. Reproduced here by oversubscribing an 8-CPU box: **203 fallbacks at 64 threads and 6474 at 128**, against 0 at 16.

  Two counters close it. `decommit_draining_` marks a thread that holds a batch, and `decommit_pending_` counts runs from **before** the queue entry is even allocated — `newDecommitEntry()` can block on the pool lock, and a run that has left its owner but not reached the free map is invisible to an allocation looking for it. `drainInFlight()` is the disjunction, and the exhausted path retries while it holds rather than giving up. Measured after: 0 at 16 threads, 0–8 at 64, and the same workload's throughput unchanged (8.2 µs per allocate+free).

  **Two plausible-sounding refinements were tried and measured worse.** Raising the retry bound from 64 to 256 changed nothing (0/27/2/15 — noise), so the bound was never the limit. Holding `na.lock` across the drain-and-take in that path — on the theory that the fast path was stealing the recovered run — took a 128-thread churn from **2.8 s to 18.5 s** and left the residual unchanged. Both were reverted.

  **The concurrent phase asserts a bound, not zero, and its thread count scales with the host.** A bounded wait cannot guarantee zero while frees are in transit, so the allowance is 0.01% (32 of 320000), above the fixed build's 0–8 spread and an order of magnitude below the unfixed 203. The thread count is 8x the CPU count because a fixed 16 made the test **blind on small machines** — 16 threads on 8 CPUs measures 0 whether or not the fix is present, which is exactly how this reached a green suite here while failing on a many-core host. **Verified as a real discriminator, probabilistically:** removing the wait fails 2 runs in 6 (544 and 497 blocks), while the fixed build passes 4 of 4. Like `test_span_descriptor_race_*`, one run is not a verdict.

  **The drain is deliberately not under the node arena lock.** It does an mprotect and an madvise per queued run, and holding the lock across that serialises every other thread allocating on that node: measured 15.0 us per allocate+free at 16 threads with the lock held, 7.6 us with it released. Nothing in the drain touches a `NodeArena` — `processDecommitEntry` takes only the free map's lock — so dropping it costs a re-check.

  **The cost of reuse is real and is the shared free map, not the drain.** Interleaved, 64 KiB blocks, 16 GiB arena so neither build exhausts: 5.0 → 6.2 us per allocate+free single-threaded (**+23%**), and 1.5–1.8 → 7.5–7.6 us at 16 threads. The pre-fix build is fast there because it *never reuses* — it bumps, which is a per-node lock, while reuse goes through `PageRunMap`'s single global lock (see "The arena's page allocator has one lock" in [performance.md](performance.md)). That speed is only available until the arena runs out, at which point the same build is both slower **and** uncompressible: on a 1 GiB arena at 16 threads it measures 13.7 us per operation with 87% of blocks outside the arena, against 8.2 us and 0% after. Sharding `PageRunMap` is what would recover the rest.

  **A bounded drain was tried and rejected.** Capping it at 32 entries per miss is ~20% faster (6.5 vs 7.6 us at 16 threads) but lets the arena march again, and once it exhausts, races between a free and the next allocation put 486 of 320,000 blocks back outside the arena. The cap trades the property the fix exists for.

- `test_malloc_numa_aligned_{full,large_only}` guard `malloc_numa_aligned(node, size, align)` (`include/smash/smash.h`): `malloc_numa` plus an alignment guarantee on the returned address. Sweeps five alignments (one page to 16 MiB) against six sizes across the routing boundaries on every online node, re-checking the whole `malloc_numa` contract on the aligned blocks — binding, physical placement with the writer pinned off-node, byte stability, cold compression and restore — plus `EINVAL` for an alignment that is zero or not a power of two. **One unexplained failure (2026-09-30)**: `large_only`, full `ctest -j4` with `SMASH_SOFTDIRTY=0` forced, footprint check "node 3: 32 live 1048576-byte blocks at 131072 alignment cost the arena 8351 pages, want 8192 (+32 slack)" — 159 pages over, i.e. more used, not the decommit-queue lag seen in `test_malloc_numa` (that makes readings low). 0 of 20 reruns (alone and with 8 busy-loop hogs). The check takes no settled reading; if it recurs, log `carved`/`free` before and after and whether a chunk was carved.

  Inside a node arena the alignment is met by over-allocating and returning the unused head and tail to **that node's** free runs, never the shared ones, which would leak the binding into ordinary allocations. The leak check is what guards that: a leak costs `align` per round trip, so at 2 MiB alignment it exhausts the 4 GiB arena the test pins by round trip ~2048, and every allocation after that falls out onto a separate bound mapping smash never compresses. **Verified as a real discriminator by source mutation:** dropping the two `free_map_.insert` calls fails with 1331–2963 of 3000 blocks outside the arena per node, and removing the alignment round-up fails 12,025 checks; restored, 3/3 runs pass.

  **The footprint check is the guard for the alignment strategy, and it must measure consumption, not address span.** The first implementation always took `num_pages + align_pages - 1` and handed the head and tail back. That costs a constant `alignment - one page` per **live** block: the returned fragments are by construction shorter than what the next request of the same shape needs, so a workload allocating one shape can never reuse them. Measured at 64 KiB alignment, +60 KiB per block whatever its size — 1.94x on 64 KiB blocks, 1.19x on 320 KiB ones, and at 128 KiB alignment +124 KiB. `PageRunMap::takeAligned()` searches for a run that already hosts an aligned start and carves only what is needed, and the node chunk cursor is rounded up with just the skipped pages donated. After: **1.00x at 64 KiB alignment for every size measured**, and 1.00x at 128 KiB for sizes that are multiples of it. Throughput unchanged within noise (6.2 us per allocate+free at one thread, 7.7-8.4 at sixteen, both before and after).

  What remains at 128 KiB alignment for a 320 KiB block (1.20x) is arithmetic, not waste: 320 KiB cannot tile a 128 KiB grid, and the gaps are ordinary free runs — 63 of 63 were taken by the next allocation that fitted.

  **An address span is the wrong metric here and looks convincing.** It equals what the blocks cost only while the node's free runs are one contiguous stretch. Once the arena has any history — the sweep, the churn check, or simply an earlier footprint probe's frees — the same blocks scatter across existing runs and the span reads up to 3.5x with nothing wasted at all. That is why `smash_numa_arena_info(node, &carved, &free)` exists: `carved - free` is exactly what a node's live blocks cost, at any arena state. **Verified as a real discriminator:** charging the alignment gap per block in the chunk-tail path fails with 14,383 pages used against 8,192 wanted.

  Two things the check deliberately does *not* assert, both measured. **Not a stable address:** `PageRunMap::take()` returns the head of the first large-enough bin with no address preference, so the aligned path legitimately cycles — 190 distinct addresses over 256 round trips, against 212 for the unaligned baseline. **Not a larger alignment:** at 16 MiB the request needs a contiguous 16 MiB run inside one node's arena, which four nodes sharing a small arena cannot always produce (47 of 1500 fell out with correct trimming), so that configuration reports fragmentation rather than a leak. `SMASH_VM_GIB=4` in the registration is load-bearing for the same reason — the default 16 GiB would hide a leak, and 1 GiB shared four ways produces false positives.

- `test_numa_compressor_{full,large_only}` guard the per-node compressor groups (`numa_compressor_test.cpp`, both modes, `SMASH_COLD_TIMEOUT_SEC=1`). It leaves a 16 MiB block cold on every node, written from off-node CPUs. Once most of each block has left RSS, it uses the diagnostic exports `smash_numa_compressor_info` and `smash_compressed_blob_for` to check, per node, that:
  - the group's threads have CPU affinity inside the node, and none of their compressions ran on another CPU;
  - the group counted at least as many compressions as the block has evicted pages;
  - worker state, page and compress buffers, and the zstd context are bound (`MPOL_BIND`) to the node, and on it wherever already touched;
  - every compressed page's blob is on the node, and reading the block back from off-node CPUs is byte-exact with every page on the node.

  Nothing after the cold wait writes to malloc'd memory. That was originally required because a write into a cold full-mode heap page could be lost (the `test_stdout_buffer_integrity_full` defect, since fixed — see that entry); it is kept because the test should not depend on that path, and an earlier version that read the node CPU lists after the wait saw an empty list in full mode.
  - **Ordinary `malloc` memory** is covered by the same test: a block per node, written from that node's own CPUs (with no binding, first touch is what places it), must end up with its blobs on that node. Measured 4096/4096 per node in both modes.
  - **Verified as a real discriminator** on a 4-node host:
    - disabling `routeByNode` sends every blob of the ordinary blocks to the shared store's node: 0 of 4096 on-node for three of the four blocks, and a pass only for the block that happens to share that node;
    - capping the node-query batch per range instead of rolling it does the same — the bug this actually caught;
    - not pinning the group threads fails the affinity check on all 4 nodes, and the off-node-compression check on 3 of them;
    - storing node blobs in the shared store leaves most blobs off the node on every node, from 2234 of 2901 to 3221 of 4096;
    - a node allocator that doesn't bind its memory fails the working-memory binding check;
    - letting the default workers compress node chunks failed the compression-count check in 3 of 3 runs, but on only one or two nodes per run, so that check is probabilistic;
    - pointing `storeOfBlob` at the shared store is **not** detectable, and should not be: `CompressStore::release` forwards by region owner, so the stale lookup costs one extra call and corrupts nothing. Before that routing existed this mutation passed the test while silently letting two stores mutate one region's free list under different locks.
  - Skips on single-node hosts (CI runners), when `mbind` is refused, and with `SMASH_NUMA_COMPRESSOR=0`.

- `test_numa_compressor_yt_hints` (`numa_compressor_test.cpp` with `NUMA_YT_HINTS=1`, large-only, `SMASH_WRITE_TRACK=yt`, `SMASH_YT_NODE_HINTS=1`, `SMASH_STATS_SIGNAL=1`; root, two or more nodes and the youngtrace module with `page_meta=Y`, skips otherwise) guards node hints taken from the yt scan: the whole test runs as above, and over the ordinary blocks' phase (two stats dumps, fd 2 pointed at a file only for each `raise(SIGUSR2)`) `node_query=` must have asked `move_pages` about fewer pages than a quarter of the blocks' compressed pages, and `node_hints=` must have set some, while the blobs stay on their node (the existing check). **Fails as of 2026-10-26** on claudepc (root, 2 nodes, `page_meta=Y`), with the youngtrace module both before and after its #86 fix: the block first touched on node 1 has 0 of 4096 blobs on its node. The module reports one run across both blocks with its first page's node (node is not in its run key; a request over the node-1 block alone reports node 1), and the run members' guesses fill the unknown hints with it. Open until one is chosen: node in youngtrace's run key, exact hints only, or a `move_pages` check of each run's last page.
- `test_malloc_override_{full,large_only}` guard that interposition actually takes effect, and that each mode routes where it claims to. Ported from mimalloc's `test/main-override.c` (`malloc_override_test.cpp`): the original allocates through plain `malloc`/`free`/`strdup`/`realloc` and asserts every pointer lands in mimalloc's own heap via `mi_is_in_heap_region` — i.e. that the calls did not fall through to libc. The allocation sequence is kept unchanged; the ownership predicate becomes smash's exported `smash_arena_for()`. Dropped from the original: `mi_version()` (forced the mimalloc link), `_expand()` (MSVC-only) and `mi_stats_print()`; the cross-API section degenerates to a malloc/free pair because smash has no second API — it *is* malloc.

  **It also guards that every aligned entry point is interposed, not just malloc.** `aligned_alloc` is versioned `GLIBC_2.16` by glibc while smash's map listed it in the `GLIBC_2.2.5` base node, so a caller bound `aligned_alloc@GLIBC_2.16`, ld.so silently used libc's, and **every `aligned_alloc` block was invisible to smash** — never tracked, never compressed, with nothing reporting it. The same class of bug as the `pthread_create@GLIBC_2.34` thread-cache leak, and alloc8's own build already documents it for this exact symbol. Fixed by moving `aligned_alloc` into the map's existing `GLIBC_2.16` node (a second node of that name is a link error), and only where the arch baseline is below 2.16 — on aarch64 the base version *is* `GLIBC_2.17`, so the bare name in the base node is already what callers bind.

  Note what the check has to be: **ownership, not alignment**. libc's own `aligned_alloc` returns a correctly aligned, perfectly usable block, so an alignment-and-usability test passes either way — the earlier 4536-allocation aligned sweep did, while every one of its `aligned_alloc` blocks came from libc. The test asserts `smash_arena_for(p) >= 0` for `posix_memalign`, `aligned_alloc`, `memalign` and `operator new(align_val_t)`, at a 2 MiB size so it holds in large-only mode too. **Verified as a real discriminator:** putting `aligned_alloc` back in the base node fails both registrations with "returned a block smash does not own".

  Stronger than the original in one way: it asserts **opposite truths per mode**, so it guards large-only *routing* and not just interposition — a small allocation must be smash-owned in full mode and must **not** be under `SMASH_LARGE_ONLY=1` (it passes through to the system allocator), while a 2 MiB block must be owned in both. A test that only ever asserted "owned" would pass vacuously in large-only. **Verified as a real discriminator:** inverting the full-mode sense fails with exit 1, and `smash_arena_for()` returns −1 for stack addresses, raw `mmap` results and `NULL` while returning a real arena id for malloc'd memory. Needs no mimalloc checkout — the port removed every mimalloc dependency.

- `test_double_free_full` guards the opt-in double-free detection (`double_free_test.cpp`, registered with `SMASH_DOUBLE_FREE=warn`). A double free is **undefined behaviour** in C and C++, so detecting it is a debugging aid, not a conformance requirement: glibc aborts (`free(): double free detected in tcache 2`), smash historically absorbed it silently. Detection is therefore **off by default** — no correct program can trigger it, so no correct program should pay for it.

  There are two detection points, and which one fires matters. A plain `free(p); free(p);` never reaches the slab: both pointers sit in the per-thread cache lane, so `ThreadCache::deallocate` scans the lane (bounded by `kPerLaneDepth`) when the policy is enabled. `Span::deallocate` tests the bitmap bit (1 = free) before setting it, catching a repeat free that survives a lane drain and a free of an interior pointer that maps onto an already-free slot; that check is essentially free because the function already loads and stores that word. On detection the second free is **dropped** — not politeness but correctness, since falling through would also run `--allocated_count`, underflowing it and corrupting the full/empty transitions in `Slab::deallocateOne`.

  The test forks the offending child (so `abort` cannot take the test process down) and asserts all three policies: `warn` reports, drops, and leaves the allocator consistent (4096 same-class allocations, no duplicate pointers); unset is silent; `abort` dies by signal. **Verified as a real discriminator by source mutation** — neutering the lane scan makes it fail with the intended message, restoring it makes it pass. An env-var-based discriminator does *not* work here: the test sets `SMASH_DOUBLE_FREE` per child, overriding anything passed from outside.

  **Measured cost of enabling it** (20M alloc/free pairs of one size class, so nearly every free hits the lane, runs interleaved to expose drift): `off` 15.15 / 15.24 ns/pair, `warn` 14.76 / 14.25 ns/pair — no measurable cost, with the two `off` runs agreeing to 0.6%. mi-stress is unchanged within noise (17 s → 18 s full, 7 s → 7 s large-only).

- `test_external_mapping` (uses a live compressor) exercises the `SMASH_TRACK_EXTERNAL=1` registration path. The ctest invocation sets the env var; without it the test would silently no-op (registration path gated).
- `test_malloc_compression` and `test_large_only_compression` are the **same executable** (`mode_compression_test.cpp`) run twice, differing only in `SMASH_LARGE_ONLY` (`0` = full, `1` = large-only — the production-supported config). The mode is read from the env at runtime, never a compile flag, so the two modes execute byte-identical assertions and cannot drift apart in coverage. The body allocates large chunks (≥ 1 MiB, so they clear `kLargeAllocVmThreshold` and enter the compressible VmRegion in **both** modes) interleaved with small chunks (≤ 16 KiB — smash slab in full mode, system passthrough in large-only). It sleeps past `SMASH_COLD_TIMEOUT_SEC`, sends `SIGUSR2`, parses `compressed=N` from the stats line, asserts `N > 0`, then verifies a byte-exact read-back of **both** classes — proving full-mode slab integrity / large-only passthrough is never corrupted, and that fault-decompress restores the compressed large chunks. (Registered via the `add_mode_compression_test(name, large_only)` helper in `tests/CMakeLists.txt`.)
- `test_compression_ratio` (in-process, direct-linked, no compressor thread) compresses a realistically-compressible page with LZ4 and zstd and asserts the achieved ratio against the paper's RQ2 figures (evaluation.tex: LZ4 4.7–12.3×, zstd-1 8.8–20.4×). Two-tier: a hard floor that fails the test (2.5× LZ4 / 4× zstd — catches "stored uncompressed" regressions) plus a WARN if it falls short of the paper's best-case number. Also asserts byte-exact roundtrip. Unlike `test_malloc_compression` (which only checks compression *happened*), this pins the codec *ratio*.
- `test_fault_cycle` / `test_fault_cycle_eager_reclaim` — the real fault path, in-process: compress a page, read it, and require a genuine SIGSEGV/SIGBUS that the handler decompresses. One binary, run with default (deferred) reclaim and with `SMASH_DEFERRED_RECLAIM=0`. Each cycle ticks until the page is **really inaccessible** (no read permission in the process's own mapping table: `/proc/self/maps` on Linux, `mach_vm_region` on macOS), then asserts the read went through the fault handler (a fault counter), the data is byte-exact, and the page is live again.

  It was disabled from June to September 2026 as "signal-delivery timing varies across CI environments". There was no timing involved. It assumed three ticks leave a page protected, and neither mode does: under eager reclaim a COMPRESSED page stays readable until the deferred-madvise sweeper protects it, so the read succeeded without a fault, the page stayed COMPRESSED, and the old "state after read" check failed **20/20** — reproduced by rebuilding the commit just before the disable. The data was always correct, and a write in that window does fault and is kept. Under deferred reclaim the page is COMPRESSED_SHADOW (still mapped read/write) after three ticks, so the old test's read never faulted and **the test passed without exercising the fault handler at all**. **Verified as a real discriminator:** with the fault handler made to restore one corrupted byte, the old test still passed in the default mode; the new one fails in both modes (`data mismatch at offset 7`). Measured passing 130/130 before re-enabling, idle, 2× CPU-oversubscribed, pinned to one busy core, and on a 2-CPU host as user and root.

## aarch64 / page-geometry guards

Five tests cover the class of bug that makes an application under libsmash throw `std::bad_alloc` on aarch64. There is exactly one way smash produces that exception — the operator-new wrappers in `src/linux_syscall_wrappers.cpp` do `void* p = xxmalloc(sz); if (!p) throw std::bad_alloc();` — so the exception always means **smash's malloc returned nullptr**. These tests attack the arch-dependent geometry that makes it do so.

The root risk is that `kPageSize` is a **compile-time** constant (`ALLOC8_PAGE_SIZE`), and alloc8 hard-codes `4096` for *every* Linux target including aarch64 — while aarch64 kernels commonly use 16 KiB or 64 KiB base pages (RHEL/Rocky/Oracle aarch64 ship 64 KiB). Every `mprotect`/`madvise` smash issues is then sub-page-aligned and rejected with `EINVAL`, and `VmRegion::ensureCommitted()` ignores `commitPages()`' return value and advances its watermark anyway, so callers get PROT_NONE memory back.

- `test_page_size` (unit, no preload) — the constants. Asserts `1 << kPageShift == kPageSize` (config.h derives the shift with a ternary that only knows 4 KiB and 16 KiB, so a 64 KiB build silently gets shift 12), `kPageSize == sysconf(_SC_PAGESIZE)`, that this machine's addresses fit the hard-coded `kAddressBits = 48` `PageMap` L1 table (which is indexed with no bounds check), and that every size class still has a valid span geometry — a class whose span holds zero objects makes `Slab::allocate()` return nullptr forever. Verified as a real discriminator: rebuilding it against a patched `ALLOC8_PAGE_SIZE` of 65536 fails on both the shift and the kernel mismatch, 16384 fails on the mismatch alone.
- `test_vm_granularity` (unit, no preload) — the same mismatch at the syscall level. Issues the exact reserve → commit → protect → decommit sequence `VmRegion` and the compressor depend on, at `kPageSize` offsets 0/1/2/3/7/15/31/63 into a reservation. Verified as a real discriminator: built with `ALLOC8_PAGE_SIZE=1024` on this 4 KiB-page host (the same smaller-than-kernel relationship as a 4 KiB build on a 64 KiB kernel) every non-zero offset fails with `errno=22 EINVAL`.
- `test_alloc_contract_{full,large_only}` — the direct regression test for the reported symptom. One executable (`alloc_contract_test.cpp`) run twice, differing only in `SMASH_LARGE_ONLY`, same one-body-two-modes contract as `mode_compression_test`. Sweeps 163 sizes across every routing boundary (size-class edges ±1, `kMaxSmallSize`, `kLargeAllocVmThreshold`, page multiples for 4/16/64 KiB pages) through `malloc`, `operator new`/`new[]`/nothrow/`align_val_t`, `posix_memalign`, `aligned_alloc`, `calloc`, `realloc` grow/shrink chains, and sustained mixed churn — asserting none ever yields nullptr or throws, and that every block is correctly aligned, fully writable, and byte-stable.
- `test_aligned_alloc_footprint_{full,large_only}` — footprint, not correctness. **`SmashHeap::memalign()` used to route every allocation with alignment > `kMinAlignment` (16 B) to `LargeAlloc`**, which rounds up to a whole page, so an ordinary `alignas(64)` 64-byte object cost a full kernel page — 66× amplification and an mmap/munmap pair per object. Fixed; see "Aligned small allocations come from the slab" in [allocation-paths.md](allocation-paths.md) below. The test now asserts a 4× per-object ceiling under interposition, which the old routing fails at 66×, in addition to the original 384 MiB hard budget and WARN. The budget alone could never catch this: 66× passed it comfortably on a 4 KiB-page host and only failed on a 64 KiB-page kernel, which is how the cost stayed in the tree documented rather than fixed.
- `test_vm_exhaustion` — `SMASH_VM_GIB=1` caps the contiguous arena at 1 GiB and the test allocates 1.5 GiB of live 4 MiB chunks, forcing `LargeAlloc`'s direct-mmap fallback; config.h names this failure by name ("exhaust the region and trigger malloc=NULL → std::bad_alloc"). Also covers the mixed arena/fallback free routing (issue #84's class) by freeing everything and reallocating. Self-evidencing: phase 1 sorts the chunk addresses and requires at least one discontinuity, since arena chunks are bump-allocated adjacent — with `SMASH_VM_GIB=16` it reports 0 discontinuities and correctly fails rather than passing on coverage it never exercised.

Only the first and last page of each chunk is touched in `test_vm_exhaustion`, so reserving 1.5 GiB costs a few MiB of RSS.

A sixth test, `test_esr_write_bit`, covers a different aarch64 gap found while reading the same code — not a `bad_alloc` route. `FaultHandler::signalHandler` classifies each fault as a read or a write for the compressor's soft-dirty ROI re-dirty signal, but the decode was x86-only (`gregs[REG_ERR]` bit 1), so on aarch64 `faultWasWrite()` stayed `-1` for every fault and the sole reader (`recordRedirtyForPage`) counted every decompress as a write. Safe — an over-reported re-dirty defers compression — but blind: a read fault would have kept its blob valid and should not have been scored as churn. `aarch64EsrWriteBit()` decodes ESR_EL1's WnR bit (bit 6) out of the `esr_context` record the kernel puts in `sigcontext::__reserved`, walking the `_aarch64_ctx` chain by hand rather than including `<asm/sigcontext.h>` (which conflicts with the signal includes, per the note on `faultWasWrite`). It reports unknown rather than guessing when WnR carries no information — a cache-maintenance fault (CM bit set), or an exception class that is not a data or instruction abort. The decoder is a pure function over bytes, so the test feeds it synthetic signal frames and runs on any host; there is no aarch64 CI runner, and the aarch64 branch of the handler itself is therefore unbuilt by CI.

## Hugepages, VMA pressure, and buffered-stdio integrity

Follow-ups for the case where the application allocates hugepages with `mmap`. All Linux-only; they skip cleanly elsewhere.

- `test_hugepage_mmap` — application hugepage mappings under the mmap interposer. The interposer's filter (`isTrackableMapping()` in `src/linux_syscall_wrappers.cpp`) takes anonymous writable mappings and **skips `MAP_HUGETLB`**. It did not always: `registerLinuxExternalRange()` walks a mapping in 4 KiB strides, so under `SMASH_TRACK_EXTERNAL=1` every 4 KiB slice of an application hugepage mapping used to be registered as an external page and marked ACTIVE. hugetlb VMAs require huge-page-aligned addresses and lengths, so *every* page operation smash then performed on them was rejected — verified directly on a host with hugepages reserved: `mprotect` → EINVAL, `madvise(MADV_DONTNEED)` → EINVAL, `mmap(MAP_FIXED|MAP_ANON)` → ENOMEM. The test asserts that the app's `mmap(MAP_HUGETLB)` still succeeds, that its data stays byte-exact (smash's restore path is `remapPages()`, i.e. `MAP_FIXED|MAP_ANON`, which would shred a hugetlb VMA if the kernel allowed it), and that allocation keeps working. It also moves one mapping with a same-size `mremap` to a huge-aligned address (growing a hugetlb mapping is EINVAL; kernels that refuse the move too get a NOTE and skip it). Skips when the host has fewer than 8 hugepages free (CI runners have none; `sysctl -w vm.nr_hugepages=N` to exercise it).
- `test_hugepage_no_mprotect_storm` — same binary with `SMASH_TEST_STRICT_HUGEPAGE=1`, which turns wasted page operations on hugetlb pages from a WARN into a failure; this is the regression guard for the skip. Nothing records that a page is unmanageable, so a registered hugetlb slice is retried every tick forever: before the fix a 16 MiB mapping produced **8192 failing page operations in six seconds** and kept going, while the slices held VmRegion's `kTrackMaxPages` = 128 Ki-page external budget (512 MiB at 4 KiB pages) despite being permanently uncompressible. Now it produces 0.

  The skip needs a second half. `mremap`'s flags cannot say `MAP_HUGETLB`, and the `mremap` interposer used to register the destination of any move or growth unconditionally, so moving a hugetlb mapping re-registered it. It now tracks a moved or grown range only if the source was tracked (`vm->contains(old_addr)`), which carries the `mmap` filter's verdict across the remap. **Verified as a real discriminator for each half:** with the `MAP_HUGETLB` skip removed the strict test sees 8192 failing operations and fails; with only the `mremap` gate removed it sees 1024 — from the single moved 2 MiB mapping — and fails; with both it sees 0. Ordinary anonymous mappings grown by `mremap` are still tracked and compressed (both halves leave RSS, as before). A file-backed mapping grown by `mremap` stayed resident *before* the gate as well, so the gate is not claimed to fix a demonstrated file-mapping problem — only to keep the filter's verdict.
- `test_vma_pressure` — crossing `vm.max_map_count` makes `mmap` return ENOMEM, which makes `malloc` return nullptr, which makes `operator new` throw `std::bad_alloc`; `compressor_thread.h` also records the resulting restore livelock ("VMAs pinned at the 65531 cap"). smash mitigates this with soft-dirty tracking (default ON), chunked Phase-3 `mprotect`, and a mid-loop VMA budget in `reclaimShadowRange()`, but nothing pinned them in place. Drives a 576 MiB compress-and-refault workload including a THP-hinted region (a partial `mprotect` inside a transparent hugepage splits it, up to 512 VMAs per 2 MiB) and asserts the VMA count stays far below the cap. Measured peak on x86-64 with defaults: 218 VMAs, against a budget of 8192 and a cap of 1048576 — a naive one-VMA-per-page implementation would produce ~131072.
- `test_stdout_buffer_integrity_large_only` / `test_stdout_buffer_integrity_full` — glibc allocates stdout's 4 KiB buffer with `malloc`, so in full mode it is an ordinary slab object. An application writing in bursts separated by quiet stretches lets that page go cold and be compressed while it still holds unflushed bytes. **Fixed**; both registrations are enabled and this is the regression guard.

  The cause was not compression losing writes — it was **shutdown reinstating a stale snapshot over live data**. `drainAllForShutdown()` handled `COMPRESSED` and `COMPRESSED_SHADOW` identically: decompress the blob, `restorePageContents()` over the page. But a shadow page is still mapped PROT_RW and holds the application's *live* bytes; nothing faults on a write to it, so its blob goes stale silently and only `reclaimShadowRange()`'s `content_matches` check ever notices — and a page that is never reclaimed is never checked. At exit the drain therefore reverted the buffer to a snapshot taken five marker lines earlier: 228 of 513 bytes flushed as NUL, 4 of 9 marker lines lost, *identically on every run*. The drain now mirrors `handleFault`'s `COMPRESSED_SHADOW` case and `reclaimShadowRange()`'s mismatch branch — keep the page, drop the blob — and deliberately has no `remapPages()` fallback there, which would discard the very bytes being preserved.

  **The knobs that look like they should matter do not, and that is a trap worth remembering**: `SMASH_SOFTDIRTY`, `SMASH_DEFER_MADVISE`, `SMASH_DEFER_MADVISE_TICKS`, `SMASH_NO_DECOMMIT`, `SMASH_MADV_FREE`, `SMASH_NO_MONITOR`, `SMASH_FIXAV` and `SMASH_P2_CHUNK` all produce *byte-identical* output, because every one of them steers an arm of the non-deferred `else` in `compressPage()` while `SMASH_DEFERRED_RECLAIM` (default ON, defined in `include/smash/config.h`) takes the `if`. Byte-identical results across supposedly different configs mean the flag is inert, not that the suspect is innocent. The flags that do discriminate are `SMASH_DEFERRED_RECLAIM=0` and `SMASH_DEFERRED_RECLAIM_DELAY`; `DELAY=100000` (never reclaim, so the page keeps its *oldest* blob) made it predictably worse — 399 NUL with the boundary at offset 114 rather than 228 at 285.

  **Verified as a real discriminator:** reverting only the drain's shadow branch, rebuilt in a scratch tree with identical cmake flags alongside a fixed control built the same way, reproduces 228 NUL at offset 285 on every run and fails the test with 2 failures, while the control is byte-perfect.

  **Independently reproduced on unmodified third-party code**, which is the stronger evidence: mimalloc's `test-stress` (the `USE_STD_MALLOC=1` build) with stdout redirected to a file, run under the pre-fix library with `SMASH_DEFERRED_RECLAIM_DELAY=100000`, emits 177 bytes of which **53 are NUL** from offset 124 to EOF, identically on every run; the post-fix library is byte-identical to a no-libsmash control. The surviving prefix is the tell — it ends with mi-stress's one-line banner **printed twice**. The blob snapshotted the buffer while it held the banner; glibc then flushed, rewound `_IO_write_ptr` and wrote the progress lines; the drain reinstated the old page contents under the newer write pointer, so the banner's bytes reappear where the progress lines belong and the file length (which lives in the `FILE` struct, never reverted) stays correct. Ordinary mi-stress at the default reclaim delay is **not** affected — the page has to still be `COMPRESSED_SHADOW` at exit — which is why this went unnoticed while the suite was green. The corruption is deterministic, so a byte-identical reproduction is the right bar here; note that `strace` perturbs it away entirely. It re-execs itself rather than plain-forking (fork clones only the calling thread, so a forked child has no compressor thread and never compresses anything) and inspects the child's output file after it exits, because the damage only appears at the exit-time flush.

Every end-to-end test in this group calls `setvbuf(stdout, nullptr, _IONBF, 0)` on entry. That was originally forced by the defect above — full mode would zero the tail of a test's own buffered output and eat its verdict lines while it still exited 0 — and is kept as hygiene now that it is fixed, so a regression on this path can never silently swallow a failure message.

## Mid-size bins, the NUMA node hint, and the stdio retry

Four defects found by a code review of this branch (2026-09-22), each reproduced by the test below before it was fixed.

- `test_mid_bins_on` sections 4 and 5 — **realloc of a binned block.** `SmashHeap::realloc` computed the old size as `is_large ? large_size : classSize(size_class)`, which knows nothing of `SMASH_MID_BINS` chunks: their `size_class` is `largeSizeClass(pages)`, 43 for every chunk, and `classSize(43)` reads past the 36-entry table. `getSize()` had already been fixed for this; realloc never calls it. All three sites now share `SmashHeap::blockSize()`.

  **The obvious test does not catch it, and that is the trap.** In the build where it was found the out-of-table read returned `0xffede9d9` (~4 GiB), so `memcpy` copied `min(garbage, new_size)` = the whole *new* size: the old bytes all arrive, and section 4's byte check passes 30 of 30 on the broken code. The damage is an over-read of the neighbouring blocks, and near the arena's commit edge into reserved pages. Section 5 watches for that directly: it fills one whole chunk of a class nothing else uses (8 × 240 KiB), waits until the neighbours have left RSS, grows the first block, and requires the neighbours to stay out. **Verified as a real discriminator:** the unfixed library faults 60 pages back in (exactly one neighbour); fixed, 0 — as root on claudepc too (3 of 3 each way).

  **Allow the prefetch window, and only it.** The first version required *zero* neighbour pages back and failed as root with exactly 2: faulting the old block's last page makes `prefetchAdjacent()` decompress up to `kPrefetchWindow` (2) pages either side within the span, and a mid chunk is one span. Unprivileged it never showed up, which is how it passed locally. The check now excludes pages within two of the block and requires the rest to stay out of RSS; the defect still shows as 58 pages locally and 60 as root. Section 4 is kept because a different build could produce a short garbage length instead, and then it is the one that fails.

- `test_mid_bins_reclaim` (`mid_bins_reclaim_test.cpp`, `SMASH_VM_GIB=1`) — **an emptied chunk handed back to the arena must release its blobs.** `MidAlloc::reclaimEmptyChunks()`, run from VmRegion's exhausted hook, returned a chunk's pages without the compressor's release hook that `LargeAlloc::deallocate` and `Slab::releaseSpan` both call. An idle chunk is exactly what gets compressed, so every blob leaked and the pages went back to the free map still `COMPRESSED`/`COMPRESSED_SHADOW`. The test compresses 40 × 320 KiB blocks, frees them, exhausts the arena with 64 MiB requests (too large for the reclaimed runs, so nothing reuses the pages before they are inspected), and requires that no page of the old chunks still reports a blob; then it puts 2 MiB blocks on the reclaimed runs and checks them byte-exact through a compress / fault cycle. It fails setup rather than passing vacuously if the blocks never compress or the arena never runs out. **Verified as a real discriminator:** unfixed, 3200 of 3200 pages keep their blobs; fixed, 0. The reuse check passes on both builds here — the leak is what is deterministic, not the corruption.

- `test_numa_compressor_{full,large_only}` second round — **a bound page's node is its binding, not the fault-time hint.** The fault handler records the faulting CPU's node in `page_node_` (`notePageNode`), and `routeByNode` trusted that hint even for `malloc_numa` pages, so one off-node read of a bound page sent its next compression to the reader's group and its blob to the reader's store. The first round never saw it because the hint is only written by the read-back at its end; the second round lets the read-back blocks go cold again and checks the blobs. **Verified as a real discriminator:** unfixed, 4095 of 4095 blobs off the node on every node, in both modes; fixed, 0.

- `test_stdio_buffer` (`stdio_buffer_test.cpp`, full mode) — **every stdio reader, wrapped or not, must survive a stream whose data arrives after its buffer could have gone cold.** glibc allocates the buffer in `_IO_file_doallocate` and fills it with an internal `read`; smash recovered only inside the readers it wraps. Seven children, one per reader (`fgets`, `getline`, `getdelim`, `fscanf`, `getc_unlocked`, `fgets_unlocked`, `fread_unlocked`), each in a fresh process: 8 MiB of 4 KiB blocks written, half freed, 3 s idle, then a `popen` of a command that sleeps 2 s and prints a line; the data must arrive, the stream's buffer must not be in the arena (`smash_in_arena`), and a 4 MiB `new[]` and `malloc` made right after must be in it (smash's versioned `operator new` aliases did not store their caller, so they followed the leftover stdio call site to the system allocator: 7 of 7 `new_in_arena=0` without the store). **Fresh processes matter**: run one after another in one process, the readers after `fgets` passed because `fgets`'s retry had warmed the memory the next buffer reused. Unfixed: 6 of 7 lost with errno 14, all 7 buffers in the arena. Mutations, each caught: the range never resolved (6 lost, every buffer in the arena); no check in `callsiteArena` (the same); the fast path ignoring `kStdioArena` (every child fails without reporting: arena 255 indexes past the slab table); `_Znwm`/`_Znam@GLIBCXX_3.4` without `ALLOC8_SET_CALLER_RA` (found by `test_vm_exhaustion`, which failed on the first version of the routing).

- `test_stdio_chk` (`stdio_chk_test.cpp`, full mode, `-D_FORTIFY_SOURCE=2`) — **fortified `__fgets_chk` / `__fread_chk` must recover like `fgets` / `fread`, and keep glibc's overflow check.** With stream buffers out of smash, the two cases where the kernel still writes smash memory: `__fgets_chk` on a `popen` stream given a malloc'd buffer by `setvbuf`, with the child sleeping 6 s so a buffer warmed before the call goes cold again during it (needs the retry), and `__fread_chk` of 12000 bytes from a regular file into the start of a 2 MiB block left until those pages are out of RAM (glibc reads straight into the caller's buffer; on a pipe it never does, which is why the first version of this case passed with glibc's own function). Plus: `__fgets_chk` told 8 bytes and asked for 64, and `__fread_chk` asked for 32 of 8, must abort with SIGABRT — on a 64-byte heap buffer, since on the stack the canary would abort a missing check too. Mutations, each caught: no stdio retry; `__fgets_chk` and `__fread_chk` each routed to glibc's; either overflow check dropped. Unfixed (no wrappers): 6 of 6 reads lost, errno 14. `test_chk_interposition` checks the two bind to libsmash.

- `test_stdio_partial_retry` (`stdio_partial_retry_test.cpp`) — **the stdio EFAULT retry must never repeat, skip or hide bytes.** See `retryStdioOnEfault` in `linux_syscall_wrappers.cpp`. Three hazards, all injected deterministically with `fopencookie` and compared against glibc's own function (`dlopen`'d, so it bypasses smash):
  - item granularity: `fwrite(buf, 8192, 1)` that wrote 4096 bytes before the EFAULT returns 0 items and was retried in full — 12288 bytes out. `fread` and `fgets` returned data from later in the stream the same way;
  - glibc's failed flush resets the write pointers and discards bytes an *earlier* call accepted, so retrying a zero-progress `fwrite` turned glibc's error into a success with 4096 bytes missing;
  - `fgets` returns NULL whether or not it consumed part of the line.

  **Verified as a real discriminator:** 10 failures on the unfixed library, 0 fixed.

  **The positive controls matter as much as the hazards.** An intermediate fix retried only streams that had no buffer before the call. It passed every hazard case, and broke the case the retry most needs: a reader blocked in `fgets` past the cold timeout, whose already-allocated buffer is compressed while it waits, so the kernel's copy of the writer's data returns EFAULT. That is real, not hypothetical — `test_stdio_after_compression`'s pipe phase (a reader blocked 8 s) got NULL with errno 14 on 2 of 2 runs under that fix, and passes on both the original code and the final fix. The controls therefore require recovery on a stream with an existing, empty buffer as well as on a fresh one. The final fix counts progress exactly instead: `fread`/`fwrite` in bytes, `fwrite` never retried with output pending, and `fgets` on an empty buffer split into one character (the only refill that can fail having consumed nothing, retried) and the rest (not retried), under the stream lock.

  **Since 2026-10-15 stream buffers glibc allocates are not smash memory** (`test_stdio_buffer`), so `test_stdio_after_compression` passes with the retry disabled (measured): it no longer guards the retry. This test (its faults are injected, independent of where the buffer lives) and `test_stdio_chk` (a `setvbuf` buffer, a direct read) do.

  **Cost, measured interleaved** (`fwrite` of 47 bytes to `/dev/null`, `fgets` over a 2M-line file, pinned, large-only): the first version of the fix cost `fwrite` 28 → 43 ns. ~6 ns was `flockfile` around the pending check, now an unlocked read (the lock would only decide which caller hears of a loss another thread's buffered bytes suffered); ~9 ns was the compiler turning `bytes == total ? nmemb : bytes / size` into an unconditional 64-bit `div` plus `cmov`, now a branch. After: 28.1 → 28.9 ns for `fwrite`, `fgets` unchanged within noise (43–45 ns; the lock is taken only when the buffer is empty).

  The functions are called through `dlsym`'d pointers: `_FORTIFY_SOURCE` rewrites a direct `fread`/`fgets` into `__fread_chk`/`__fgets_chk`, which smash deliberately does not wrap.

## Per-CPU run cache

- `test_run_cache_{off,on,on_full,on_softdirty0}` (`run_cache_test.cpp`) guard `SMASH_RUN_CACHE_MIB` (see [design-run-cache.md](design-run-cache.md)). One body; the expectation follows the variable, so "off" must mean off.
  1. **Reuse**: a 4 MiB block freed warm and reallocated at the same size on the same CPU (the test pins itself) comes back as the same block, with a hit, still on its node — and re-touching it takes **0 minor faults**, against **1024 of 1024** without the cache, because today's path decommits. - `yt_stream_test` (`yt_stream_test.cpp`, unit, no kernel) guards the reader of the scanner's output (`compress/yt_stream.h`) on streams built in the module's layout: young 4 KiB, run and THP items reported with their page counts, old and non-present items not, high metadata bits masked off the address, the same result fed 1, 7, 8, 24, 119, 120, 121 bytes at a time and whole; a cut status, a stream ending inside a record's items, a foreign record magic and a zero-length run each detected. **Verified by mutation**, each failing: old items reported; high bits kept in the address; a run read as two words; the status word ignored; `complete()` ignoring items still expected. - `test_phase3_batch` (`phase3_batch_test.cpp`, `SMASH_SOFTDIRTY=0`) guards Phase 3's arming cost: 256 MiB of contiguous idle memory must be made PROT_READ with at least 64 pages per `mprotect` (read from the `[smash pipeline]` line's `p3 armed=/calls=`, prompted with SIGUSR2, stderr pointed at a file). `flushPhase3Run` grouped pages into runs of 16 but protected each page on its own; on the 128-core arm64 box (30M watched pages, 500k mappings) that made compressor ticks take 68-142 s and compression crawl (0.8 GiB in 15 minutes). ## Data integrity under load

- `test_integrity_stress`, `_small_heap`, `_large`, `_large_sd0`, `_idle` (`integrity_stress_test.cpp`, about 30 s each, the small heap 60 s) guard the one property every compressor change can break: data read back as last written while many threads use it and the compressor compresses, reclaims and restores it. Every 4 KiB unit of every block carries (tag, version) and a pattern derived from them, with the expected versions in mmap'd memory outside smash; small objects and "survivors" (256-byte objects left one per page, the rest freed) carry the same. Threads keep a hot block, touch cold units, read shared blocks that every thread faults on, rewrite all their cold data in synchronized waves, round-trip units through `pwrite`/`pread`, `realloc` and free blocks; then everything is checked at the stop and again after idling until 90 % is compressed. It fails on any wrong byte, on fewer than `STRESS_MIN_RESTORES` accesses that found their page compressed, and if under half the cold data is compressed after idling. Variants: full mode; a full-mode heap of about 4 MiB (2 threads, 256 KiB blocks, `SMASH_LARGE_ALLOC_VM_THRESHOLD=65536`, no survivors); the application's configuration (`SMASH_LARGE_ONLY=1 SMASH_SUBARENAS=1 SMASH_DIRTY_MAX_MIB=64 SMASH_CODEC=lz4`); the same with `SMASH_SOFTDIRTY=0`; and with `SMASH_WRITE_TRACK=idle` (root only; unprivileged it falls back). All use three test-only knobs: `SMASH_TEST_TICK_MS=50`, `SMASH_TEST_WORKERS=8`, `SMASH_TEST_JITTER_US=200` (agents/config.md).

  **Idle phase (2026-10-19).** After the stop the test waits up to `STRESS_IDLE_SEC` (default 180, was 30) for 90 % of the cold data to be compressed again, stopping as soon as it is. A wait longer than 5 s prints every 5 s the cold units' page states, idle counts and restore counts (`smash_page_info`), and with `SMASH_STATS_SIGNAL=1` smash's stats at its start and end. Why: on the 128-core arm64 box, `SMASH_WRITE_TRACK=idle`, 128 threads x 64 MiB, `STRESS_SEC=1800` failed once with "only 0% of the cold units compressed after idling" (100 s runs and 64 threads passed). The breakdown showed every one of 2152668 units ACTIVE with idle count 0 for 30 s, the first 4188 counted idle at 30.2 s; ticks took 5-9 s, nearly all of it Phase 1's idle scan (46 us per page over the run, 86 us when idle). The final read-back makes every page accessed, and the scan (K=4) needs about two passes of four ticks to find a page idle again: 30-70 s there. A timing failure, 0 wrong bytes. Reproduced on claudepc as root with `SMASH_TEST_TICK_MS=8000` (2 threads x 64 MiB): the 30 s test failed with 0 %, the new one reached 100 % at 57 s. The 1800 s run at the same size on the x86 VM (soft-dirty, 50 ms ticks) re-compressed 90 % in 8.7 s; restore counts there reached 4-5 on 13 % of units (none above 3 at 100 s), and the back-off they impose is counted in ticks, so it is short only while ticks are.

  **Verified by mutation** (each run 20-30 s):
  | mutation | full mode | small heap | application config |
  |---|---|---|---|
  | Phase B race put back (chunks from `start / 64`, no lower bound: the 2026-10-16 defect) | 0 of 3 | **14 of 20** at 30 s (registered settings, now run for 60 s); with 2048 survivors 4 of 6 | 0 of 2 |
  | restore makes the page readable before writing the data back | 2 of 2 (183-189 bad) | | 2 of 2 (238-338) |
  | Phase B marks pages COMPRESSED and unlocks them before `madvise`/`mprotect` | 2 of 2 (23-153) | | 2 of 2 (100-110) |

  The two ordering mutations are caught with no knobs at all (132-165 and 5 bad per run). The Phase B race is not: getting it into a test took three findings, each measured against the mutant.
  1. **It needs a tiny heap.** Worker A handles the boundary chunk first in its range and worker B last in its own, so they meet only when B's walk is short. With the default 256 MiB, 0 of 3 even with every knob; the original repro (`thrash_backoff_test`, 512 KiB sets) and the small-heap variant have each worker's range near one chunk. In the application configuration sub-arenas grow the heap in 64 MiB grid chunks, which plausibly keeps the default workers' boundaries chunk-aligned there (0 of 2).
  2. **It needs pages that stay compressed.** A page the race hit reads zeros until something reads it; at the 1 s tick the only hits came from survivors (one 256-byte object per page, idle for many ticks: 1 of 3 runs, against 0 in about 25 runs without them, which matched the original repro's lost pages). At the 50 ms tick the shared blocks, written once and only read, are enough: 14 of 20 without survivors (9 of 10, then 5 of 10: the rate is noisy), 4 of 6 with 2048 of them (a bigger heap), so the small-heap variant runs without, for 60 s. One run is not a verdict: about 70 % per 30 s.
  3. **It needs ticks.** Phase B runs once per tick, so a 20 s run at the default 1 s tick gives 20 chances. With 2048 survivors and `SMASH_TEST_TICK_MS=50`: 4 of 4 and 7 of 8 (20 s); the tick alone (adaptive workers, no jitter) 3 of 3; tick and 8 workers without jitter 5 of 8. Jitter adds a little (7 of 8 against 5 of 8) and costs one relaxed load per syscall when off. `SMASH_TEST_WORKERS=8` makes worker boundaries exist on a 2-CPU host, where the adaptive count rarely exceeds 1.

  Two traps: a `std::set`-style harness on the mutant crashes instead of reporting (its own nodes sit on the zeroed pages: "[smash FATAL] ... null"), which is why this test keeps every expectation outside smash; and the original repro hit the race 1 of 4 rounds without knobs, so "it passed once" means little for either library. On the fixed library: 15 of 15 runs (5 variants x 3) clean, the suite as root on claudepc (normal and UBSan, `track=idle` confirmed from the stats line), and two 10-minute soaks (2026-10-17): the application configuration on the 4-node x86 VM (2.68M accesses found their page compressed, 1.71M shadow, 0 wrong) and full mode on the 2-CPU claudepc (1.64M and 0.45M, 0 wrong).

  **Soak**: the same binary with `STRESS_SEC=1800` (or more) under any variant's environment, e.g. `LD_PRELOAD=build/libsmash.so SMASH_LARGE_ONLY=1 SMASH_SUBARENAS=1 SMASH_DIRTY_MAX_MIB=64 SMASH_CODEC=lz4 SMASH_TEST_TICK_MS=50 SMASH_TEST_WORKERS=8 SMASH_TEST_JITTER_US=200 SMASH_DEFER_PHASES_MS=0 SMASH_COLD_TIMEOUT_SEC=1 STRESS_SEC=1800 build/tests/integrity_stress_test`. On a large host raise `STRESS_THREADS` (at most 16 by default) and `STRESS_MIB`; drop the knobs to run at production timing.

## Simulator

- `test_smash_sim_smoke` / `test_smash_sim_smoke_run_cache` / `test_smash_sim_smoke_subarenas` run `smash_sim` (see [simulator.md](simulator.md)) for 2 s at 8 threads over 4 simulated nodes, with 10% of frees reported as compressed, 20% freed by another thread and 30% through the shared arena — cache off, cache on, and sub-arenas (2 per node, 20 ms decay, 4 MiB cap, so purges, partial purges and pooled chunks all happen). They fail if any invariant does: a page handed to two live blocks, a free whose page map entry is not its span, a carved page not free after the full drain, or no progress (a hang). **Verified by planting bugs**: a run cache that returns a run without removing it (caught as a hang: the double hand-out corrupts the free map into a cycle), and a trim that drops runs (caught as leaked pages on every node). With sub-arenas, also the sub-arena free lists (every run in a chunk its sub-arena owns, no page listed twice across dirty, clean, tails and the chunk pool, each counter equal to its runs), checked before and after a full purge, and nothing dirty after it: planted, a purge that skips (338 MiB still dirty), a free sent to the wrong sub-arena (caught only by the pre-purge check — a full purge pools whole chunks whoever held their runs) and a dirty run handed out without being removed (crash, exit 139).

  Their first run found that `smash_numa_arena_info`'s "free" left out the unused tail of a node's newest chunk, so `test_malloc_numa_aligned_*`'s footprint check (`carved - free` before and after) could not see a block served from the tail. Fixed in `VmRegion::nodeArenaInfo`; the footprint tests pass on the corrected numbers.

## Coverage: the diagnostics are the least-tested code

Measured 2026-09-20 with `gcovr` over a `--coverage -O1` build running the full
suite: **66% of lines under `src/`**, and **72% of the lines added that day**.
The gaps are not random — they are almost entirely the *things-have-gone-wrong*
paths, which is exactly the code that runs while diagnosing a crash:

| new code | line coverage |
|---|---|
| `describeFaultAddress()` (`smash_heap.h`) | 9% |
| `[smash FATAL]` print (`fault_handler.h`) | 0% |
| `warnArenaExhausted()` + `arenaFreePages()` / `arenaLongestFreeRun()` | 0–16% |
| `BootstrapAlloc::reportExhausted` | 0% |
| metadata-exhaustion null guards (`large_alloc.h`, `slab.h`) | 25–28% |
| Round 6 syscall wrappers (`linux_syscall_wrappers.cpp`) | 86% |
| `walkPathForFault` / `walkUnsizedForFault` (`syscall_compat.h`) | 100% |

Whole-file lows worth knowing: `compression_roi.h` 44%, `src/compress_only/`
0% (compress-only mode has no test), `util/alloc_failure.h` 0%,
`fault_handler.h` 56%.

The fault diagnostics were verified by hand instead (a program that faults at
a null address, at an unmapped address, and past its own block), and all three
classify correctly — including `page N of M, state S` for the arena case. Note
`si_code` in that line: **1 = SEGV_MAPERR** (nothing mapped — a wild pointer),
**2 = SEGV_ACCERR** (mapped, wrong permissions — smash's own protection). On a
SIGBUS the same field separates `BUS_ADRALN` (1, misaligned — an unaligned
atomic, which faults on aarch64 and does not on x86-64) from `BUS_ADRERR` (2,
past the end of a file mapping).

A **latent SIGBUS** worth knowing about, though it is opt-in and off by
default: `SMASH_SPILL=1` pre-`fallocate`s its file precisely so ENOSPC cannot
become a SIGBUS through the MAP_SHARED mapping — but a drained region is
hole-punched (`FALLOC_FL_PUNCH_HOLE`) and then reused, and the write that
refills it needs fresh blocks. On a full filesystem that write is a SIGBUS.
